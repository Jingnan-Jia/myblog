# 实验设计书：Idea 10 检索增强的 LLM 优化求解器选择（OptiRetrieve）

## 0. 摘要
本项目提出 OptiRetrieve：给 LLM 求解器生成加一层"问题-求解器"可检索示例库，用相似历史问题做 few-shot 检索，再以 OptiHive 式统计建模选优，把 OptiHive 的一次性生成与 RAG 复用结合。构建优化问题库（NL4OPT/MAMO/多车场 VRP 变体），问题嵌入检索 top-k 相似历史问题作为 in-context 示例，批量生成候选求解器，用统计模型（伯努利/混合模型）估计真实最优率并选优。在可验证的优化问题集上，对照 LLM 直接生成、OptiHive 原版、检索无统计选择、迭代修复基线，主指标为最优率 + 可行率。无训练或极轻量，4×L40 跑本地 7B–30B 生成与验证，投稿 AAAI 2027 / IJCAI 2027。

## 1. 研究背景与动机
### 1.1 问题定义
LLM 求解器（LLM4CO）从自然语言问题描述自动生成优化模型/求解代码，但生成不可靠，常依赖高延迟的迭代修复。OptiHive 用"单次批量生成 + 统计选择"替代迭代修复，但不复用历史问题；工业实践中大量相似问题重复出现，历史求解器是宝贵资产。问题：如何让 LLM 求解器生成"借用相似历史问题的最优求解器"作为示例，再统计选优？

### 1.2 相关工作不足
- OptiHive（NLP I · 论文 15 · OptiHive: Ensemble Selection for LLM-Based Optimization via Statistical Modeling）每次从零生成、不复用历史、无检索组件。
- "Optimization Modeling with RAG"（arXiv:2608.00015）证明 RAG 示例让建模准确率 40%→72%，但无统计选择、无不确定性量化。
- LLM4CO 基线普遍靠迭代修复（延迟高）；SCHEDBench（arXiv:2608.00991）评 NL 约束保真，MuEvo（arXiv:2608.03636）做演化启发式集成但非 RAG。
- 上下文工程综述（arXiv:2607.24791 企业级 RAG）证明"问题-解决方案库复用"是工业刚需。

### 1.3 为什么是现在、为什么你的环境适合做
- 证据：OptiHive（AAAI 2026）确立"统计选择"范式；RAG 版优化建模（arXiv:2608.00015）证明检索增益；两者未结合是明确空白。
- 环境：无需训练或极轻量；本地 7B–30B 求解器生成与求解验证（可用 OR-Tools 等开源求解器）在 4×L40 上并行；DeepSeek/Kimi 负责问题库生成与示例标注，成本低。

## 2. 研究目标与可验证假设
- H1（RAG 增益）：检索相似问题做 few-shot 后，求解器最优率高于零样本直接生成。成立时观测：最优率提升 ≥ +10 个点（对标 arXiv:2608.00015 的 40%→72% 量级）。
- H2（检索+统计选择协同）：统计选择 + 检索示例的组合优于各自单独。成立时观测：组合版最优率 ≥ 单用其一 ≥ +5 个点。
- H3（统计优于多数投票）：统计模型（伯努利混合）选择优于简单多数投票。成立时观测：最优率提升 ≥ +3 个点。
- H4（可解释选择）：统计模型输出的"组件置信度"与真实性能相关。成立时观测：置信度与最优率的 Spearman ρ ≥ 0.5。

## 3. 总体方法设计
### 3.1 语料/数据流水线
1. 优化问题库：NL4OPT、MAMO（官方）+ 自建多车场 VRP 变体（DeepSeek 生成问题描述 + OR-Tools 验证最优解）。
2. 示例-求解器对：对库内问题用 LLM 生成候选求解器 + 求解验证，标注"哪个求解器最优"，构建检索库（约 2000 条）。
3. 示例标注（Kimi K2.6）：给每条问题打"问题结构标签"（目标类型/约束类/规模）供双通道检索。
4. 检索库 embedding：用 bge-m3 编码问题描述 + 结构特征向量。

### 3.2 方法设计
- 双通道检索：结构特征（one-hot/分类标签）+ 语义 embedding 余弦；融合 = λ·结构 + (1−λ)·语义，λ 初值 0.4。
- few-shot 注入：top-k（k=3）相似问题的"描述 + 最优求解器代码"进 prompt。
- 批量生成：同 OptiHive，一次生成多样化解集（求解器、问题实例、验证测试）。
- 统计选择：伯努利/混合模型估计每个候选求解器的真实最优率，选最高者；对检索示例的"先验成功率"作为贝叶斯先验注入。
- 不确定性：bootstrap 置信区间（1000 次）。
- 验证器：OR-Tools 求精确最优（小规模）或 CP-SAT 上界；不可验证问题排除。
- 超参数初值：k=3、λ=0.4、候选解数 10、bootstrap 1000、temperature 0.7。

### 3.3 训练流程
- 无训练；可选：对 bge-m3 做领域自适应 embedding 微调（可选，1 GPU·天）。
- 全部为生成 + 验证 + 统计推理。

### 3.4 评测流程
- 主评测：可验证优化问题集（NL4OPT 求解器可验证子集、MAMO、多车场 VRP 变体）。
- 指标：最优率（Optimality Rate）、可行率（Feasible Rate）、求解延迟。
- 消融：检索 k、示例数、统计模型 vs 多数投票、是否 RAG。

| 数据集 | 来源 | 许可 | 用途 |

## 5. 基线复现
| 基线 | 官方代码 | 预期最优率（复杂 VRP，粗估） |
|---|---|---|
| LLM 直接生成（零样本） | 自建（Qwen2.5-7B/30B） | ~10–30% |
| OptiHive 原版 | arXiv:2508.02503（自实现统计选择） | ~40–70% |
| RAG 示例（无统计选择） | 自建（检索 top-k + 多数投票） | ~35–65% |
| 迭代修复基线 | 自建（LLM 反馈循环 ≤5 轮） | ~25–50% |
| OptiRetrieve（本项目） | 自建 | ~55–90% |
- 复现步骤：OptiHive 按论文实现（批量生成 + 伯努利模型）；迭代修复基线用标准 self-debug 提示。
- 统一口径：同一生成器（Qwen2.5-30B 或 DeepSeek API）、同一验证器（OR-Tools）、同一时间预算（如每问题 ≤120s）。

## 6. 实验矩阵
- A（主实验）：OptiRetrieve vs 基线，3 问题集（NL4OPT/MAMO/多车场 VRP）。
- B（消融）：检索 k（1/3/5/10）；双通道 vs 单通道；统计模型（伯努利/混合/多数投票）；是否 RAG。
- C（鲁棒性）：问题描述噪声（模糊 NL）；约束不一致；检索库规模（500/2000）。
- D（泛化性）：跨生成器（7B/30B/API）；跨问题类型（0-1 KP→TSP→VRP 迁移）；检索库领域外问题。

## 7. 评测协议
- 最优率：候选求解器在验证实例上达到已知最优的比例。
- 可行率：求解器能输出可行解的比例。
- 延迟：生成+验证耗时（中位数）。
- 统计选择指标：选择的组件最优率、置信度-性能相关性（ρ）。
- 统计：3 种子；均值±std；配对 bootstrap p<0.05。

## 8. 算力与资源计划
- 4×L40：本地 7B/30B 求解器生成 + 验证并行 ≈ 2–3 GPU·天；可选 embedding 微调 1 GPU·天；消融 ≈ 1 GPU·天；合计 3–5 GPU·天。
- 存储：检索库 + 求解结果 <20GB。
- API：问题库生成 + 示例标注（DeepSeek）≈ 150–300 美元；Kimi 标注 + judge ≈ 100–200 美元；合计 ≤ 500 美元。
