# 实验设计书：Idea 12 自演化检索摘要索引（Evolving Index）

## 0. 摘要
本项目提出 Evolving Index：让 RAPTOR/HTSIR 式多粒度摘要树随"新内容流入 + 查询反馈"在线生长/合并/修剪，实现持续学习的长期记忆 RAG。定义三类索引演化算子（split/merge/refine），由"查询命中分布 + 新文档流"驱动，带探索-利用平衡策略（高命中子树细分、低价值簇合并），演化决策经 LLM 自评价闭环校验。在 QMSum、LongBench 多文档子集、自建"流式文档+查询"持续 QA 场景上，对照 RAPTOR、HTSIR、固定索引 + 周期性全量重建，主指标为随文档流长度的检索 Recall@k 与生成 F1，消融演化成本与策略。轻量、无大模型训练，约 2–3 GPU·天，投稿 SIGIR 2027 / ACL 2027。

## 1. 研究背景与动机
### 1.1 问题定义
RAG 的摘要树索引（RAPTOR/HTSIR）是静态一次性构建的：文档流持续进入（新闻/邮件/日志），索引若不更新则新知识检索不到；若周期性全量重建则成本随规模上升。且查询日志包含宝贵反馈——高命中的子树说明该区域价值高，低命中的簇应合并。问题：如何让摘要树根据"新文档流 + 查询反馈"在线演化（split/merge/refine），在持续学习场景下保持检索与生成质量？

### 1.2 相关工作不足
- RAPTOR（arXiv:2401.18059）、HTSIR（NLP I · 论文 41 · Improving Long-Context Summarization with Multi-Granularity Retrieval Optimization）的树均静态构建、无演化。
- 图 RAG 侧 LEDGER（arXiv:2606.28379）做到依赖图局部更新但非摘要树、面向 agent 编辑。
- 上下文工程综述（arXiv:2604.20874 "Root Theorem of Context Engineering"、arXiv:2605.00505 denoising-first）指出"持续上下文/自演化"是本质需求；企业级 RAG 报告（arXiv:2607.24791）强调知识库日更。
- 现有增量工作（如 GraphDelta 本主题 Idea 4）聚焦属性图三元组编辑，本 idea 明确差异化：聚焦"文档摘要树 + 查询日志驱动"。

### 1.3 为什么是现在、为什么你的环境适合做
- 证据：持续学习型 RAG 索引是 2026 明确前沿；LEDGER（ACL 2026）刚点燃"局部更新"方向；"查询日志驱动索引优化"几乎无人做。
- 环境：演化全靠 DeepSeek 摘要生成与决策（API），无需训练；4×L40 用于 7B 生成评测与可选重排器，资源富余。

## 2. 研究目标与可验证假设
- H1（演化胜固定）：随文档流增长，演化索引的检索 Recall@k 显著高于固定索引。成立时观测：文档流 10k 条后 Recall@10 领先 ≥ +5 个点。
- H2（查询驱动有效）：查询命中驱动（高命中细分、低价值合并）优于随机演化。成立时观测：查询驱动版 Recall 比随机版高 ≥ +3 个点。
- H3（精读不损）：演化后的簇摘要质量（LLM 自评）不劣于全量重建。成立时观测：摘要一致性 ≥95%（自评），与全量重建差 ≤1 点。
- H4（成本可控）：演化成本显著低于周期性全量重建。成立时观测：演化 token/延迟 ≤ 全量重建 30%，质量差 <2 点。

## 3. 总体方法设计
### 3.1 语料/数据流水线
1. 初始树：DeepSeek 对种子文档构建多粒度摘要树（块 256 token → 簇摘要 → 根摘要，树深 ≤3）。
2. 文档流：自建"流式文档+查询"持续 QA 场景（新闻/技术文档流 + 按批到达的查询日志，1000→10k 文档，10k 查询）。
3. 查询日志：DeepSeek 按主题批生成查询（覆盖新旧文档），Kimi K2.6 记录"哪个子树被命中"。
4. 演化日志：每轮演化记录（split/merge/refine 决策 + 质量自评），供离线分析"哪些查询类型受益"。

### 3.2 方法设计
- 演化算子：
  - split(子树)：子树查询命中率高且簇内语义发散 → 细分（LLM 重摘要子簇）；
  - merge(簇)：低价值簇（命中率低、与兄弟簇语义接近）→ 合并重摘要；
  - refine(簇)：新文档定位到簇 → 增量更新簇摘要（prompt：`Update cluster summary given new document, keep concise`）。
- 驱动信号：命中分布（查询命中的子树计数）、新文档流（新增块定位到叶→向上触发 refine）、簇语义熵（嵌入方差）。
- 探索-利用平衡：以概率 ε（初值 0.1）随机选演化候选，其余按价值排序选；价值 = 命中率 × 语义熵。
- LLM 自评价闭环：每次演化前用 DeepSeek judge 评估"演化是否提升簇质量"，不通过则回滚；评估 prompt 输出 0–4 分，≥3 才保留。
- 超参数初值：块长 256、树深 ≤3、ε=0.1、分裂命中阈值 5 次/窗口、合并语义阈值 0.9、窗口大小 100 查询。

### 3.3 训练流程
- 无大模型训练；LLM 调用为主。
- 可选：小 cross-encoder 重排器（1 GPU·天）。
- 4×L40 跑 7B 生成评测 + 演化评测并行。

### 3.4 评测流程
- 随文档流长度的曲线：文档流 {1k, 2k, 5k, 10k} 各测一次检索 Recall@10 + 生成 F1。
- 固定索引对照：同文档流下不演化（含周期性全量重建 5k/10k 两档）。
- 演化成本：token 消耗、延迟、演化操作次数。
- 离线分析：按查询类型（新旧知识/单跳/多跳）分组报告演化收益。

## 5. 基线复现
| 基线 | 官方代码 | 预期 Recall@10（10k 文档，粗估） |
|---|---|---|
| RAPTOR（静态） | github.com/parthsarthi03/raptor | ~55–65% |
| HTSIR（静态） | 论文（自实现） | ~58–68% |
| 固定索引 + 周期全量重建 | 自建 | ~62–72% |
| Evolving Index（本项目） | 自建 | ~68–78% |
- 复现步骤：RAPTOR 官方 repo 构建静态树；HTSIR 自实现两阶段摘要树；周期重建用同一 DeepSeek 摘要管线。
- 统一口径：同一生成器（Qwen2.5-7B）、同一检索器（bge-m3）、同一 top-k、同一评测脚本。

## 6. 实验矩阵
- A（主实验）：Evolving Index vs 基线，随文档流 {1k,2k,5k,10k}。
- B（消融）：演化算子单独（split/merge/refine）；探索率 ε（0/0.1/0.2）；驱动信号（仅查询/仅文档流/两者）；自评价闭环开/关。
- C（鲁棒性）：文档流主题漂移（突变 vs 渐进）；查询分布偏移；噪声文档注入。
- D（泛化性）：跨生成器（7B→13B）；跨域（LongBench 子集）；树深（2/3/4）。

## 7. 评测协议
- 检索指标：Recall@5/10、nDCG@10。
- 生成指标：F1/EM（对应数据集标准）。
- 演化指标：操作次数、演化 token 消耗、延迟（中位数）、回滚率。
- 摘要质量：LLM 自评分（0–4）+ 人工抽检 100 条 κ。
- 统计：3 种子（查询日志采样）；均值±std；配对 bootstrap p<0.05。

## 8. 算力与资源计划
- 4×L40：生成评测 1 GPU·天；可选重排器 1 GPU·天；消融/鲁棒性 1 GPU·天；合计 2–3 GPU·天。
- 存储：树 + 日志 <20GB。
- API：摘要/演化决策/自评（DeepSeek）≈ 300–600 美元；查询日志 + 质量复核（Kimi）≈ 100–200 美元；合计 ≤ 800 美元。
