# 实验设计书：TimingBomb —— 多智能体软件开发系统的"时序炸弹后门"与关键节点防御

## 0. 摘要

本实验设计书在 AAAI 2026 收藏论文 IMBIA（Special Track on AI Alignment · 论文 84 · Shadows in the Code: Exploring the Risks and Defenses of LLM-based Multi-Agent Software Development Systems）基础上，提出"时间/逻辑延迟激活"的代码后门类型学与关键智能体防御。核心创新：① 时序/条件后门类型学（触发条件：用户输入模式 / 时间 / 数据状态），覆盖 IMBIA 缺失的攻击维度；② 跨智能体"后门传播图"——攻击代码如何在设计→编码→测试→部署环节传播并放大；③ 形式化关键智能体定位（图论：删除某智能体对后门传播的最大削减）并给出针对性防御验证。在 ChatDev / MetaGPT / AgentVerse 上验证，总预算 ≈2–3 GPU·天，投稿目标 ICSE 2027 / ISSTA 2027 / CCS 2026。

## 1. 研究背景与动机

### 1.1 问题定义

威胁模型：多智能体软件开发系统（MASD，如 ChatDev/MetaGPT/AgentVerse）由多个 LLM 智能体（产品经理/架构师/编码员/测试员等）协作开发软件。攻击者以两种身份之一参与：**MU-BA（恶意用户 + 良性智能体）**——通过恶意需求/输入污染系统；**BU-MA（良性用户 + 恶意智能体）**——某个智能体已被攻击者控制（或代码级后门已植入一个智能体的输出策略）。

IMBIA 的攻击是"即触发即生效"的隐蔽功能；本设计的攻击是**部署后延迟触发**：生成的代码在开发阶段看起来完全正常、通过测试，但满足特定条件（特定输入模式 / 特定时间 / 特定数据状态）时在部署环境中触发恶意行为。评测现实漏洞：如数据库操作、定时任务、特定用户权限下的行为篡改。

### 1.2 相关工作不足

- **（Special Track on AI Alignment · 论文 84 · IMBIA）**：系统研究 MASD 风险，定义 MU-BA/BU-MA 场景并提出 Adv-IMBIA 防御；但攻击是即时生效、评测主观、防御为启发式，未覆盖时序后门。
- **PlanFlip（arXiv:2607.16199）**：多智能体规划阶段 prompt injection，不针对代码后门。
- **BadChain（arXiv:2401.12242）**：单 LLM 的 CoT 后门，不涉及多智能体协作与代码生成。
- **空白**：① 无 MASD 的时序/条件后门类型学；② 无"后门如何在多智能体流水线中传播放大"的机制分析；③ 无"关键智能体定位"的图论形式化与针对性防御。

### 1.3 为什么是现在、为什么你的环境适合做

- **时机**：MASD 正在成为软件工程主流（2026 年），IMBIA 刚建立风险框架；时序后门是"安全-软件工程"交叉的新攻击面，评审（ICSE/ISSTA）对 MASD 安全有明确兴趣。
- **环境**：ChatDev/MetaGPT/AgentVerse 均为开源，Qwen2.5-14B 本地后端在 4×L40 并发跑多 Agent 会话；30 个真实软件需求任务 × 3 框架 ≈2 GPU·天。
- **无模型训练**：攻击与防御都是"提示/代码级"，完全符合算力约束。

## 2. 研究目标与可验证假设

1. **H1（时序后门可实现）**：存在三类延迟触发后门（用户输入模式 / 时间 / 数据状态），使"短测试窗口内正常、条件满足时触发"，触发后 ASR ≥ 80%。
   - 成立时可观测结果：测试窗口内正常率 ≥ 95%（通过测试）、条件满足时 ASR ≥ 80%；三类后门均验证。
2. **H2（传播机制可建模）**：后门在"设计→编码→测试→部署"环节的传播可被"后门传播图"精确刻画（节点=智能体/环节，边=后门转移概率）。
   - 成立时可观测结果：传播图覆盖的环节 ≥ 3；模拟传播路径与实测触发路径一致率 ≥ 80%。
3. **H3（关键智能体可定位）**：图论"删除节点对后门传播的最大削减"能定位出 1–2 个关键智能体，针对性防御（在该节点插桩）使触发 ASR 下降 ≥ 50%。
   - 成立时可观测结果：关键智能体命中的真实放大节点 ≥ 1；防御后 ASR 下降 ≥ 50%、正常任务成功率下降 ≤ 5%。
4. **H4（优于启发式防御）**：关键节点插桩 + 依赖图监控优于 IMBIA 的 Adv-IMBIA 启发式防御（ASR 下降更多或同等但误伤更低）。
   - 成立时可观测结果：防御后 ASR 对比 Adv-IMBIA 提升 ≥ 10 个百分点或误伤降低 ≥ 30%。

## 3. 总体方法设计（详细到可复现）

### 3.1 数据/对抗样本流水线

1. **需求集**：自建 30 个真实软件需求（电商/教务/库存/报表/定时任务等，覆盖数据库操作与用户权限语义）+ 公开 App 生成任务集（ChatDev 官方示例）。
2. **时序后门类型学构造（3 类）**：
   - T1 用户输入模式触发：特定用户输入（如用户名="admin_tmp"）触发恶意分支（如权限提升）。
   - T2 时间触发：`datetime.now()` 超过某日期后，定时任务改为篡改数据。
   - T3 数据状态触发：某字段达到阈值（如订单金额>1000）时触发盗取/篡改逻辑。
   - 后门以"提示注入需求"（MU-BA）与"恶意智能体输出策略"（BU-MA）两种方式注入。
3. **测试集**：每个需求生成 20 条测试（15 条正常 + 5 条触发），短窗口测试 = 只跑 5 条正常（模拟测试窗口）。
4. **生成用 DeepSeek V4 Flash**：批量生成需求文本与测试用例。

### 3.2 攻击/算法设计

- **模块 1：后门注入器**：按类型学把恶意代码段（含触发条件）嵌入生成需求/智能体提示；对 MU-BA 用"隐藏后门的需求描述"（LLM 包装成正常功能），对 BU-MA 用"恶意智能体角色提示"。
- **模块 2：后门传播图（本文核心）**：
  - 节点 = MASD 流水线环节（设计/架构/编码/测试/部署）+ 各智能体；
  - 边 = "后门代码/提示从 A 环节流入 B 环节"的观测转移（在 30 任务上统计）；
  - 构建方式：在每任务中跟踪"含后门的代码/需求"经过哪些环节仍保持活性；
  - 输出：带权有向图 + 每个节点的"后门放大系数"（该节点输出中后门相关代码占比）。
- **模块 3：关键智能体定位（图论）**：
  - 问题：`argmax_i [传播图删除节点 i 后的后门可达率下降]`；
  - 用删除-重算（node-removal）近似 + 传播模拟（随机游走/传染病模型）交叉验证；
  - 输出：关键节点排序表。
- **防御实现**：
  - 关键节点插桩：在定位的关键智能体输出加"安全审查"（LLM 代码审计 + 规则扫描）；
  - 运行时行为基线：对生成的代码做动态监控（触发条件出现时告警）；
  - 依赖图分析：报告后门传播路径供审计。

### 3.3 训练/注入流程

- 无大模型训练；本地 Agent 后端 Qwen2.5-14B（4×L40 并发多 Agent 会话），ChatDev/MetaGPT/AgentVerse 版本锁定。

### 3.4 评测与防御对照流程

- 运行：30 任务 × 3 框架 × 4 条件（干净 / T1 / T2 / T3）× 2 注入方式（MU-BA/BU-MA）。
- 判定：Kimi K2.6 判"后门是否被激活 / 输出是否被污染"；代码级判定：静态分析（正则 + LLM 代码审查）标记后门代码。
- 防御对照：关键节点插桩 / 运行时基线 / 依赖图分析 vs Adv-IMBIA。

## 5. 基线复现

| 基线 | 出处 | 复现步骤 | 预期指标 |
|---|---|---|---|
| IMBIA（即时后门） | 收藏 Align · 84 | 复现其注入方式与评测 | 即时 ASR 93%/45%/71%（对应三框架） |
| PlanFlip 规划注入 | arXiv:2607.16199 | 复现规划阶段注入 | 规划被改写、无时序后门 |
| Adv-IMBIA 防御 | 收藏 Align · 84 | 复现其启发式防御 | 对即时后门有效、对时序后门弱 |
| 本设计（TimingBomb） | — | 时序后门 + 传播图 + 关键节点防御 | 触发 ASR ≥80%、防御后下降 ≥50% |

统一口径：全部基线用同一 30 需求集、同一框架版本、同一 Kimi 判定脚本；ASR 判定与 IMBIA 一致（基准输出对照）。

## 6. 实验矩阵

- **A（主实验）**：3 后门类型 × 2 注入方式 × 3 框架 → 触发 ASR、窗口内正常率。
- **B（传播图验证）**：传播路径覆盖、模拟 vs 实测一致率（H2）。
- **C（关键智能体定位）**：删除-重算 vs 传播模拟 vs 随机 → 关键节点命中率（H3）。
- **D（防御对照）**：关键节点插桩 / 运行时基线 / 依赖图 / Adv-IMBIA → ASR 下降与误伤（H4）。
- **E（类型消融）**：T1/T2/T3 各自的窗口规避性（早期测试通过率）。

## 7. 评测协议

- 主指标：触发后 ASR（条件满足）、窗口内正常率（隐蔽性）、后门传播图覆盖率、关键智能体定位命中率、防御后 ASR 下降、误伤率。
- 统计：固定框架版本与种子（42/2024/2026）；每任务 5 次运行报告均值±std；ASR 差异用 McNemar。
- 判定：Kimi K2.6 裁判 + 代码级静态分析双确认；人工抽检 100 例。

## 8. 算力与资源计划

- 本地：30 任务 × 3 框架 × 4 条件 ≈2 GPU·天（Qwen2.5-14B 多 Agent 并发）。
- 传播图与关键节点定位：CPU 即可。
- API：DeepSeek V4 Flash 生成需求与测试 ≈30 万 token；Kimi K2.6 裁判 ≈20 万 token；成本 < $15。
- 存储：< 20GB。
- 总预算 ≈2–3 GPU·天。

## 10. 风险与备选方案

| 风险 | 概率 | 影响 | 备选方案 |
|---|---|---|---|
| Agent 框架版本差异导致不可复现 | 中 | 高 | 锁定版本 + 固定种子 + 容器化 |
| 后门在长流水线中被测试环节删除 | 中 | 高 | 让后门藏在"测试不覆盖的路径"（条件分支中）；增加注入密度 |
| 传播图覆盖率不足 | 中 | 中 | 增加任务量到 50；把"提示级传播"与"代码级传播"分图 |
| 关键节点定位与实测不一致 | 中 | 中 | 用删除-重算与传播模拟交叉验证；报告 top-3 而非单点 |

## 11. 论文写作计划

- **目标会议**：ICSE 2027（截稿约 2026-08）、ISSTA 2027、CCS 2026（软件安全向）。ICSE 为软件工程主投，CCS 为安全兜底。
