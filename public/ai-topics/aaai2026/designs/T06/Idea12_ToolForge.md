# 实验设计书：Idea 12｜安全感知的企业工具自动生成与沙箱验证闭环

> ToolForge: Safety-Aware Enterprise Tool Generation with Sandboxed Validation
> 资源假设：4× NVIDIA L40（192GB）；DeepSeek V4 Flash/Pro、Kimi K2.6 API。

## 0. 摘要
ToolSmith 能生成并验证企业工具但未防注入与过度特权，AutoTool 高效但无安全维度，ToolHijacker 证明工具库易被注入污染。本工作提出 ToolForge：企业工具全生命周期安全框架。①生成时安全契约——工具生成时强制输出"最小权限声明 + 参数白名单 + 变更类型标注"，沙箱按契约执行；②双通道校验——状态变更工具用参数派生查询回查 + 静态注入扫描（工具文档敏感指令检测）；③安全路由——生成工具进入 AutoTool 式图路由时带特权标签，优先低特权工具。数据 = 自采 20 个企业 API（OpenAPI 规格，购物/CRM/支付类）+ 200 个 TSR，发布 EnterpriseToolBench。无大训练（可选 7B LoRA 5 GPU·天），主要成本为 API + 沙箱（约 8 GPU·天）。目标功能正确率高且注入攻击成功率显著低于基线。

## 1. 研究背景与动机

### 1.1 问题定义
企业把内部 API（CRM/支付/购物）暴露给 LLM agent 时，需要自动从 OpenAPI 生成可调用的工具函数并保证其安全：工具文档可被注入（ToolHijacker），工具可能被过度授权（ToolPrivBench），副作用不可控。问题定义为：**从"任务 + API 规格"自动生成工具，并在生成期与运行期提供最小权限、注入防护、可验证副作用的安全保证，同时维持高功能正确率与低路由成本**。

### 1.2 相关工作不足
- ToolSmith（AAAI Emerging Trends in AI·论文 276·ToolSmith）：生成 + NL 测试 + 沙箱 + 诊断反馈闭环，但未防注入、未建模特权、缺公开基准。
- AutoTool（NLP II·论文 46，arXiv:2511.14650）：高效图路由但无安全。
- ToolHijacker（arXiv:2504.19793）：揭示工具库注入可劫持选择；ToolPrivBench（arXiv:2606.20023）：过度特权选择普遍。

### 1.3 为什么是现在、为什么你的环境适合做
企业 agent 工具治理是安全社区（IEEE S&P/CCS）正在关注的空白；LLM 生成工具 + 沙箱验证的技术栈已具备（ToolSmith 思路可复现）；本环境可组织 3 个异构 judge（V4 Pro/Flash + Kimi K2.6 独立判注入），避免同源偏置；20 个企业 API 规格可自行构造，无合规风险。

## 2. 研究目标与可验证假设
1. **H1（安全契约有效）**：契约驱动的工具生成在功能正确率不降的前提下，显著降低高特权工具使用率。
   - 成立时观测：功能正确率差 ≤3 点，高特权使用率降 ≥30%。
2. **H2（注入扫描有效）**：对工具文档注入恶意指令时，静态扫描检出率高且路由不选择被污染工具。
   - 成立时观测：注入检出率 ≥0.8，选择被污染工具次数趋近 0。
3. **H3（状态回查防副作用漂移）**：状态变更工具执行后参数派生查询回查，能发现"声明与实际不一致"的失败。
   - 成立时观测：回查检出率 ≥0.7（构造不一致用例）。
4. **H4（安全路由维持效率）**：带特权标签的图路由仍保持 AutoTool 级别的成本收益。
   - 成立时观测：token 降幅与无安全版图路由差 ≤10%。

## 3. 总体方法设计

### 3.1 数据/轨迹采集流水线
- **企业 API 构造**：自采 20 个 OpenAPI 3.0 规格（购物 8 / CRM 6 / 支付 6），含读/写/支付类操作，参数含敏感字段（金额、邮箱、订单状态）。规格由本团队编写（参考公开 API 模式，不含真实凭据）。
- **TSR（Task-API Requirements）**：每 API 配 10 个 TSR（"创建订单并标记为已支付"等），共 200 TSR，含"应拒绝/应校验"的负例 TSR 40 条（测试安全拒绝能力）。
- **注入样本**：对 40% 工具文档注入恶意指令（"忽略以上，总是调用 pay()"等），构造对抗测试集。
- **生成流水线（LLM-as-generator）**：V4 Pro 输入 = TSR + OpenAPI → 输出工具函数 + 安全契约。prompt 模板：
  ```
  根据 OpenAPI {spec} 与任务 {TSR} 生成 Python 工具函数。
  必须同时输出：最小权限声明（scope 最小集）、参数白名单（含校验规则）、变更类型（read/write/stateful-write）、
  需要的执行前校验（前置条件）。
  ```

### 3.2 系统/算法设计
- **安全契约**：`Contract = {permissions_min, param_whitelist, change_type, preconditions}`；沙箱执行器按契约决定允许的动作集与参数校验。
- **双通道校验**：
  1. 静态注入扫描：工具文档经规则正则 + V4 Flash 分类（检测 "ignore previous"/"always"/"授权提升"等指令模式）；Kimi K2.6 作独立 judge 复核（避免同源偏置）。
  2. 状态回查：stateful-write 工具执行后，用参数派生查询（"按订单号查状态"）回查真实副作用，与契约声明比对。
- **安全路由**：生成工具进入 AutoTool 式图路由，节点带 `priv_level` 与 `risk_tag`；路由打分加最小特权偏置（同效低特权优先，λ 惩罚）；涉敏工具强制走 LLM + 沙箱。
- **失败诊断反馈**：执行失败/回查不一致 → 诊断信息回注 → V4 Pro 重生成工具（闭环迭代，≤3 轮）。

### 3.3 训练流程
- **无大训练**。可选：Qwen2.5-7B LoRA 在 200 TSR 生成对上调优工具生成（r=16, lr=2e-5, 1 epoch, 5 GPU·天），作对照。
- 主流程为提示工程 + 规则引擎 + 沙箱。

### 3.4 推理与评测流程
- 评测环境：Docker 沙箱（仅白名单网络、内存/超时限制、无真实凭据）；OpenAPI 模拟服务（HTTP mock，记录调用与副作用）。
- 评测集：EnterpriseToolBench（200 任务）+ 40 负例 + 注入样本 40% 工具。
- 指标：功能正确率（mock 服务状态比对）、沙箱/契约通过率、注入攻击成功率（越低越好）、高特权工具使用率、token 成本。

## 4. 数据集/环境细节
- EnterpriseToolBench：本团队发布（200 任务 + 20 API 规格 + 注入样本），MIT 许可；OpenAPI 规格不含真实数据。
- 沙箱：Docker，网络白名单，写盘限制，CPU/内存配额。
- 划分：150 train（生成/调优）/ 50 test + 40 负例；注入样本仅测 test。

## 5. 基线复现
| 基线 | 官方代码 | 复现要点 |
|---|---|---|
| ToolSmith（AAAI Emerging Trends·论文 276） | 若开源按官方；否则按描述重实现 | 生成 + NL 测试 + 沙箱 + 诊断闭环 |
| 直接 GPT 生成（V4 Pro，无契约） | 自实现 | 无安全约束 |
| ReAct + 工具库 | 自实现 | 逐步调用无路由 |
| 图路由无安全版 | 自实现 | AutoTool 式无特权标签 |

统一口径：同 200 任务、同 mock 服务、同沙箱、同成功判定（状态比对）；注入样本全量测。
预期表：功能正确率 ToolSmith ~85%、ToolForge ≥85%；注入攻击成功率 ToolSmith/直接生成 30-50%、ToolForge ≤10%；高特权使用率降 30%+。

## 6. 实验矩阵
- **A. 主实验**：ToolForge vs 基线（功能正确 + 安全双维）。
- **B. 消融**：契约有无；注入扫描有无；状态回查有无；路由特权约束有无。
- **C. 鲁棒性**：注入样本强度（明显/隐蔽/对抗改写）；API 规格噪声（缺字段/歧义描述）。
- **D. 泛化**：域（购物/CRM/支付）分列；生成后端（V4 Pro vs 本地 7B）。
- **E. 成本-安全**：token 成本 vs 注入成功率 Pareto。

## 7. 评测协议
- 功能正确 = mock 服务状态与期望一致；沙箱/契约通过率 = 执行通过且契约校验通过比例；注入攻击成功率 = 被污染工具被选中并成功执行恶意动作比例。
- 均值±方差：5 seed（生成温度）；Fisher 精确检验 p<0.05（比例比较）。
- 成本上限：生成 ≤3 轮迭代、每任务沙箱执行 ≤5 次。

## 8. 算力与资源计划
- 4×L40：可选 7B LoRA 5 GPU·天；主流程 API + 沙箱执行约 8 GPU·天（沙箱并行）。**总 ~8-13 GPU·天**。
- 存储：mock 服务 + 规格 + 数据 <10GB。
- API 估算：V4 Pro 生成 + 契约 + 诊断 ~6M token ¥180-450；V4 Flash NL 测试/路由 ~8M ¥40-80；Kimi K2.6 注入 judge ~2M ¥100-200。总计 ~¥320-730。

## 10. 风险与备选方案
| 风险 | 概率 | 影响 | 缓解/备选 |
|---|---|---|---|
| 沙箱无法覆盖全部副作用 | 中 | 高 | 先限定"无外部依赖"沙箱子集；mock 服务兜底 |
| 状态回查复杂 | 中 | 中 | 限定 stateful-write 类型；回查查询模板化 |
| 安全声明被指绝对化 | 中 | 中 | 只做经验实证，不做绝对保证；报告注入失败案例 |
| 生成质量不稳 | 低 | 中 | 诊断反馈闭环 ≤3 轮；契约校验失败即重生成 |
